The error a match rate can never find

This batch reconciles perfectly. Every automated check passes. Two real errors are inside it.

Settlement batch · August 2026 36 lines · reconciled ✓
Gateway fee overcharged on one line + ₹4.12
Refund under-deducted in the same batch − ₹4.10
What the batch total looks like ₹0.02 out

Two paise. Inside any tolerance a finance team would set, so it passes silently and the money leaves. Accounting calls this a compensating error, and a total-level check cannot detect it by construction — which is why a match rate is not evidence of a correct close.

Attest catches it by rebuilding what the refund deduction should have been from the merchant's own records and the netting rule in their contract — never from the settlement report it is auditing. Use the audited document to check itself and the error cancels out of the very test built to find it.

Three numbers, and the second two are the point

Matches we broke
68.2%
Of the batches that passed, this share failed adversarial review. Published on purpose.
Why you can trust these numbers. The test data is built truth-first: the real ledger is generated and frozen, the documents are derived from it, then errors are injected into the documents only. Four defect classes were planted with no detector written for them — three were caught anyway by generic integrity checks, and one is reported as missed. Recall on the classes we designed for is 100%, which on its own proves nothing. Recall on the held-out classes is 75%. That is the number that means something.

How it works

Connect, close, claim

01 — CONNECT

Your real settlements

Attest calls Razorpay's live Settlement Recon API with your own keys. Test and live keys use the identical path. Bank statement, courier remittances and order export come in alongside.

02 — CLOSE

Every line, proven or not

Deterministic matching, then a proof chain per line, then six falsification hypotheses attacking every match that survived. The arithmetic never goes through a model.

03 — CLAIM

Money, with a clock on it

Each exception gets a counterparty, the evidence that would close it, and a deadline. Courier disputes die in 14 days — a month-end close finds them too late.

Cadence is the product. On the sample month, closing monthly instead of daily lets ₹5,365 across 16 claims expire unfiled — computed from the same findings scored against a close that lands 30 days later, not asserted. Running daily is not a performance detail. It is the difference between finding money and recovering it.

Honest scope

What exists, and what does not

A roadmap presented as a feature is a lie. This is the split.

Built and working

  • Live Razorpay Settlement Recon API, test and live keys
  • Deterministic match engine and per-line proof chains
  • Adversarial auditor — six falsification hypotheses
  • Accuracy scored against held-out ground truth
  • Deadline-aware recovery with counterparty and claim window
  • Self-contained close pack, zero runtime dependencies
  • One-command local verification of every claim

Roadmap — not built

  • OAuth, so merchants connect without pasting API secrets
  • Continuous ingest via webhooks, replacing the batch run
  • Multi-tenancy and a CA-firm view across clients
  • Filing and tracking claims, not just drafting them
  • Journal export to Tally and Zoho
  • A learning loop on which claim types actually get paid
Why the benchmark is synthetic, deliberately. Accuracy can only be measured against data whose truth you constructed. On live settlements you can report that something does not reconcile — never whether you were right, because nobody knows the correct answer. Recall needs an answer key. So the ingestion path is real and the accuracy benchmark is synthetic, by necessity rather than convenience.
