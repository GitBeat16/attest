The error a match rate can never find

One batch from this month, in full. It reconciles perfectly.

Gateway fee overcharged on one line +₹4.12
Refund under-deducted in the same batch −₹4.10
What the batch total looks like ₹0.02 out
Two real errors. The batch is out by ₹0.02 — inside any tolerance a finance team would set, so every automated check passes and the money quietly leaves. Accounting calls this a compensating error, and a total-level check cannot detect it by construction.

Attest catches it by rebuilding what the refund deduction should have been from the merchant's own refund records and the netting rule in the contract — never from the settlement report it is auditing. Batch setl_bcac82b4f08674.

Why the first number is a lie. Razorpay pays exactly what its own settlement report says it will pay, so the bank and the report agree by construction. That tie proves the money arrived. It proves nothing about whether the deductions inside were correct — and it is the number conventional reconciliation reports as success.
